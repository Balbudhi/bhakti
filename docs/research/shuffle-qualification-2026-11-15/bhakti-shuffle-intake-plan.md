## Existing media identity and checks to reuse

`apply_lossless_trim` validates original source SHA, complete listener-format population and archived originals; writes outputs and trim-applied.json with status pending/applied/no-trim, retained start/end, original SHA and output SHA per format. Extraction must run on the retained preferred listener bytes AFTER this transaction completes, never on the untrimmed original or temporary model AAC. Both no-trim and applied are explicit accepted states. A pending transaction blocks processing/publication.

`bhakti_boundary_timebase.py:29 boundary_transaction`, 57 boundary_snapshot and 65 require_boundary_snapshot provide a song lock and digest snapshot that includes the trim marker. Reuse them for input freeze/compare-before-write. They do not make multiple sidecar/reader/catalogue files automatically transactional; bundle preparation and final validation remain necessary.

`publish_media_release.py:116 publish_locked` snapshots reader/media/trim inputs, copies audio into immutable temporary files, names remote assets by SHA, checks input stability and writes data/media.json schema v2 with each src/type/sha256 (168–185). `audit_youtube_trims.py` validates saved trim-review artifacts it discovers, not a proof that every catalogue song has a complete new assessment. `audit_audio_quality.py` concerns stream quality, not tempo validity. `audit_bhakti_contract.py` concerns current reader schema/word maps/timing. ## Minimal proposed integration

One owner module `scripts/bhakti_shuffle_profiles.py` should own schemas, semantic/audio dependency projections, assessment validation, freshness, policy and public projection. A separate thin `scripts/audit_shuffle_profiles.py` should invoke that same validator over an exact catalogue population; do not duplicate rules in UI or workflow code. Optional batch CLI wraps the same operations for backfill/refresh. Names are proposals, not existing APIs.

Suggested operations: semantic_identity(accepted reader inputs, taxonomy_version); audio_identity(retained asset hash, trim identity, extractor/model/config version); assess_audio(snapshot, budget/options); assess_semantics(accepted source/gloss/English/order, taxonomy, options); validate_assessment(packet, expected_identity); project_public(accepted profile); require_publication_coverage(catalogue, profiles, policy, media_manifest).

Audio assessment starts after apply_lossless_trim and preferred_listener_audio, independently of transcript work. Use bounded local extraction unless a specifically authorized audio-model experiment is selected; independent extraction can overlap paid text stages without increasing API concurrency. Semantic assessment starts after complete_semantics and the final reviewed scripture/subject/language projection. Because these metadata overrides currently happen inside _generate, either construct a pure final reader projection shared by generation and profiling, or bind semantics only to the explicit accepted inputs and validate final emitted projection separately. Do not profile unreviewed raw transcription or pre-override subject guesses and label it final.

Both assessments are private cached artifacts, e.g. pipeline/06-semantic-profile.json and 07-audio-profile.json, plus independent review acceptance where needed. `run_one` records their outcomes. `_generate` validates pre-existing acceptance/freshness before public writes; generate-only never creates paid assessments. For a newly required song with missing/stale profiles, generate-only fails with a precise refresh command. It must not silently waive the requirement or call a provider.

A final shared public sidecar `data/shuffle-profiles.json` is generated from validated profiles, keyed by queueId (also include slug for diagnostics), with schemaVersion, taxonomyVersion, feature versions, per-song semantic/audio status and fingerprints. No queue/runtime implementation in this work. Do not add script loading, queues, controls or automatic changes to ordering. The sidecar contains compact reviewed features only, not prompts, paths, provider transcripts, excerpts, credentials or editorial disputes. Future consumers join to catalogue by stable queueId and can treat unusable feature dimensions neutrally.

Single serialized catalogue/bundle writer owns sidecar export alongside catalogue generation, rather than song workers racing on one JSON file. Explicitly include sidecar and a sanitized coverage/acceptance receipt in hosted git staging and assemble_public_site allowlists. The assembler performs final public validation over the copied snapshot before replacing _site. This catches direct style application, reader normalization, manual updates and media replacement that bypass _generate. Validate the generated sidecar and media manifest in release preparation before uploads too, so failure is discovered before external effects where possible. No private review tree should be uploaded merely to let CI inspect it.

## Mandatory assessment is not mandatory numerical certainty

Separate processing state from feature state. Processing: pending/running/failed/completed-reviewed. Feature outcome: known, uncertain/unknown, or not-applicable/unmetered. A completed audio assessment can validly report unmetered with BPM null and evidence; low-confidence half/double-tempo ambiguity can report unknown with candidates retained privately. A completed semantic assessment can have no supported theme tags, with explicit reason and completed review. Never invent BPM, key, mood or labels to pass the gate.

A crash, timeout, missing file, unsupported schema, stale identity or pending review is NOT the same as assessed-unknown. Those fail the new-intake assessment gate until successfully retried or an explicit reviewed fallback assessment is recorded with its limitations. A reviewed fallback must document what was actually examined; it cannot certify a model listened when only text was available. Validate finite numeric ranges, confidences and nullable status constraints.

This gate concerns publishing a new recording with complete honest processing. It does not authorize filtering published tracks out of playback. Future ranking must retain every selected occurrence and use neutral/missing-dimension treatment for unknown, unmetered, legacy-pending and unavailable profiles, with nonzero exploration. No hard theme/BPM membership requirement.

## Staleness and reuse

Semantic identity should hash the exact consumed source/IAST/gloss/English, language, performed occurrence order and reviewed entity projection, plus taxonomy/model/prompt/reviewer versions. Hash canonical semantic data, not all data.js bytes: changing audio URLs, HTML, queue number or whitespace should not cause a paid semantic rerun. If performed repetition influences theme salience, include repeats; if not, state that contract explicitly.

Audio identity binds actual retained listener-content SHA, trim interval/application contract, selected source, extraction windows/sample policy, extractor/model version and parameters. Publishing the same bytes at another immutable URL does not invalidate audio features. A different transcode is different bytes; reuse requires an explicit verified equivalence relationship, never a matching title/duration alone. If only lyrics change, reuse audio assessment. If only retained audio changes, refresh audio assessment and existing text/timing gates decide separately whether source review is affected. Timing-only onset fixes need not rerun themes/audio summaries unless a feature consumed those timed segments. No assumption that all audio features have one global BPM: support varying/unmetered segments.

Private cached 02/04/05 artifacts or a validated public-reader adapter suffice for theme backfill; run separate extraction against listener assets for audio features. Do NOT call full run_one or --force just to backfill profiles. That unnecessarily risks source/timing work, paid calls and historical trim adoption. Refresh stages are selected by dependency identity; unchanged accepted artifacts are reused.

## Legacy rollout

Commit an explicit baseline of legacy queueIds/slugs (initially current 337, re-captured at actual rollout) with policy version. Every current catalogue song appears in the sidecar as either accepted or legacy-pending; never fabricate assessments for old songs. All IDs absent from the pinned baseline require both completed reviewed assessments before publication. Eligibility must not depend on a caller-supplied 'legacy' boolean or mere existence of a newly created directory. Withdrawn/re-added IDs retain auditable policy status.

Legacy unchanged songs remain publishable/playable during backfill. Once a legacy song has accepted profiles, stale feature projections must be removed/marked unavailable until refreshed. Define explicitly whether an editorial change may ship with that unavailable status during migration; recommendation: permit legacy publication with explicit stale status, require current profiles for all new intake, and enable stricter per-song enforcement only on graduation. Do not accidentally freeze unrelated corrections across all337 songs. Finishing migration can make the whole population mandatory in a later explicit policy version.

## Tests that would establish this design

- New intake cannot publish with only one assessment, missing receipt, stale semantics/media/trim, pending transaction or failed extraction; assessed unmetered and reviewed-unknown DO publish without fake numbers.
- A real generate-only path reuses matching accepted artifacts with zero provider calls and rejects new missing/stale artifacts; no alternate generate caller bypasses it.
- Wrong-song profile/duplicate queueId/omitted catalogue entry/extra unknown ID/version mismatch fail. Explicit legacy-pending entries cover all baseline songs; a new slug cannot self-claim legacy.
- Real reader changes through style application and rebuilding are detected at assembly; URL-only and HTML-only edits preserve semantic/audio reuse; source/gloss/English/order and audio changes invalidate only their dependencies.
- Source-repair private candidate generation remains possible before profiling, while final publication cannot bypass required profiles.
- Interrupted assessment/bundle export and concurrent reader/media edit preserve the old valid public snapshot; final copied artifact is checked, not just pre-copy source.
- Real hosted staging includes sidecar/receipt; real assemble_public_site output includes them and excludes private evidence. A new file outside the allowlist is not sufficient evidence of successful shipping.
- Changed remote/local media hash fails until profile refresh or verified equivalence; same bytes/new URL succeeds. Missing local media in CI uses committed accepted asset-hash provenance and manifest, not a false claim CI listened again.
- End-to-end fixture: intake artifacts -> assessments -> generate-only -> catalogue/sidecar -> media manifest -> assembled site, including existing page_html caller signature. Use tiny fixture audio and deterministic extraction or a real local extractor; mocked descriptor returns alone do not qualify musical accuracy.
- Profile quality requires separate multilingual human review and devotional audio validation; schema tests cannot prove useful themes, accurate tempo, or good listening order.

Snapshot clarification: freeze exact accepted input artifact bytes under the existing song boundary lock and compute both their byte hashes and the canonical feature-dependency hashes. Use those same frozen objects to construct the reader and public profile; do not validate one read and generate from another. Prepare reader/profile/receipt outputs together, record exact emitted reader and sidecar digests in the compact release receipt, and compare source snapshots again before adoption. A presentation-only reader change may reissue this pairing receipt deterministically after proving unchanged canonical dependencies; it does not require a model call. Final assembly checks the paired output bytes and dependency projections, so a regenerated reader cannot silently retain a stale accepted profile. Use the existing locks, atomic JSON helper and staged assembly directory; no new transaction framework is needed. An interrupted multi-file working-tree update is withheld from publication by the receipt/assembly gate, rather than claimed automatically atomic.
