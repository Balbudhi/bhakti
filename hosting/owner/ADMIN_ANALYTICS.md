# Owner library breakdown and request status

The authenticated owner page shows the current public catalogue as two sorted horizontal bar lists and a pending request list. Each distinct languageTags or subjectTags label is counted once per song; missing labels count as Unspecified. Each bar shows its actual song count and percentage of all songs. Multilingual and multi-tag songs count in every applicable category, so percentages can sum above 100%. All categories stay visible, including small categories; no Other grouping or fractional allocation. Bars use the same zero-to-100% scale, cream ink on the existing red ground, visible category labels/counts/percentages, and accessible text independent of the bar. Fetch date/count are explicit; catalogue loading failure must not affect requests or imply zero songs. No new dependencies.

Pending means server status queued. Completed requests are retained in a collapsed history. Counters count requests, never inferred songs. A pending request has an explicit Mark completed action. POST /api/requests/complete sends its existing ID with the session CSRF token. Only an exact matching receipt (id/text/createdAt, completed status and valid completedAt) changes local state. Transport or malformed response leaves it pending and retryable. A confirmed completion remains completed if a later refresh fails. The removed control moves focus to the pending heading. Dynamic actions respect the existing busy guard. Session expiry clears private request DOM. Existing add-request retry may return completed; accept it without reopening, preserving a newer draft.

Backend owner R supplies completion endpoint/schema and authenticated fixed-public-URL catalogue endpoint; frontend B owns web files and scripts/test_owner_ui.js. G reviews spec/tests before implementation, then final code. First establish independently derived denominator and request transitions in the existing DOM harness; next pure breakdown + safe bar/text rendering; then completion/history UI and integrated backend tests. Root alone deploys and performs browser/live checks. No queue entries are auto-completed from titles, catalogue counts or this UI change.

Tests: five-song overlapping/deduplicated/empty-label fixture; empty catalogue; every category retained; malicious labels as text; unauthenticated no catalogue read; pending/completed partition; completed add replay; complete CSRF + exact receipt; ambiguous failure/same-ID retry; malformed receipt; confirmed completion then failed refresh; busy double click; expired-session clearing. Existing auth/import/exact-draft tests remain in force. Real HTTP storage/auth tests are backend-owned; this harness only certifies shipped client behavior.

Research rationale: Heer and Bostock, CHI 2010, experiment 1A (pp. 3–4) found common-scale position judgments more accurate than length, angle, or area judgments. Aligned horizontal bars make the endpoints comparable on a shared baseline and retain readable category text on mobile. This supports the chosen display without claiming that their experiment proved length superior to angle. https://hci.stanford.edu/publications/2010/crowd-perception/heer-chi2010.pdf


# Visitors

Contract, privacy limits and storage: `docs/OWNER_INTAKE.md`, "Visitor counts". The section uses the same single ink, hairlines and bar lists as the library breakdown; it adds no card, color or dependency. Daily counts are columns (at most 24px wide) on one labelled scale, dense above 100 days. The map answers "roughly where" only; circle area is proportional to visitors, and the country and city lists carry every value. Pointing at or tapping a mark writes its value below the figure; the Daily numbers table and the lists give the same values without a pointer. Refetching keeps the previous figures dimmed; failure removes them instead of showing zero.
